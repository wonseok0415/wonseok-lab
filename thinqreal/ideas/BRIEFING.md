# ThinQ Real 신규 아이디어 트랙 — 세션 브리핑

> **이 문서의 용도**: '자동 점검(FieldCheck)'처럼 ThinQ Real에 **추가할 수 있는 새로운
> 시스템/기능 아이디어를 논의·구체화하는 전용 트랙**의 출발 문서다.
> 새 세션은 이 문서를 먼저 읽고 시작한다. 자동 점검 트랙과 히스토리가 섞이지 않도록
> **이 트랙의 기록은 이 폴더(`ideas/`) 안에서만** 관리한다.

## 0. 트랙의 경계 (반드시 지킬 것)

- **ThinQ Real 메인 시스템(예약 관리 웹·관리자 페이지·Apps Script)은 건드리지 않는다** —
  새 기능은 언제나 **순수 추가** 방식 (새 폴더 / 새 시트 탭 / 새 엔드포인트 추가).
- **FieldCheck(자동 점검, `../fieldcheck/`)도 이 트랙의 대상이 아니다** — 별도 트랙에서
  운영 중이므로 코드·문서를 수정하지 않는다. 참고(선례)로만 읽는다.
- 이 트랙의 진행 기록은 `ideas/NOTES.md`에 남긴다.
  `thinqreal/CLAUDE.md`의 핸드오프 로그(자동 점검 트랙 중심)에는 쓰지 않는다.

## 2. 불변 제약 (어기면 운영 장애)

1. **실서비스 Apps Script 소스는 `wonseok0415/thinqreal` 루트가 유일하다.**
   이 저장소(`wonseok-lab`)의 `.gs`는 구버전 사본(안내문으로 교체됨) — **절대 배포 금지**.
2. Apps Script **배포 URL·SHEET_ID·`bookings` 탭명·슬롯 시간표는 불변**.
   재배포는 항상 "배포 관리 → 기존 배포 편집 → 새 버전" (새 배포 생성 금지 — URL이 바뀜).
3. **키·비밀번호를 코드·예시·문서에 쓰지 않는다** — Script Properties 사용 (FieldCheck의 `FC_API_KEY` 선례).
4. 백엔드 수정이 필요한 아이디어면: `wonseok0415/thinqreal` 저장소에서 **순수 추가**(새 type 분기·새 탭)로
   작업하고, 배포 전 최신 main 확인 (다른 트랙의 재배포와 충돌 방지).

## 3. 추가 방식의 선례 — FieldCheck 모델 (참고)

FieldCheck가 "메인 무변경 + 순수 추가"로 시스템을 늘린 성공 사례다. 새 아이디어도 같은 틀을 권장:

1. **설계 문서 우선** (`DESIGN.md` — 배경/구조/판정·동작 원리/이관 대비/로드맵)
2. **별도 폴더** (`thinqreal/<새이름>/`) — 메인 코드와 물리적 분리
3. 백엔드가 필요하면 **추가 전용** (새 시트 탭 + 새 엔드포인트, 기존 코드 무수정에 가깝게)
4. **기존 인프라 재활용으로 비용 0원** 지향, 신규 계정·과금 없음
5. 사내 이관 대비: 엔드포인트/인증/저장소를 설정으로 분리
6. 검증은 단계적으로: 도구 사전 검증 → 현장 실측 → 자동화 편입

## 4. 논의 출발점 (참고용 — 채택 여부는 새 세션에서 자유롭게)

빈 캔버스보다 방향 감각용으로만. 기존 자산과 공간 특성에서 나올 수 있는 갈래:

- **방문 경험**: 예약 확정~방문 사이의 사전 안내 자동화, 방문 후 팔로업, 시연 시나리오 개인화(방문 목적별)
- **운영 효율**: 시연 준비 상태 체크리스트의 시스템화, 공간·가전 사용 현황 기록, 소모품·비품 관리
- **데이터 활용**: 축적 중인 예약·설문·점검 데이터의 교차 분석 리포트, 방문 트렌드 예측
- **시연 콘텐츠**: 쇼룸 도슨트(안내) 보조 도구, 방문객용 인터랙티브 자료
- **공간 지능화**: 환경 데이터(온습도·조도 등) 로깅과 시연 품질의 상관 분석
