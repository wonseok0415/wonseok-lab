# FieldVoice 운영 설계 — 전용 노트북 공용 운영·사내 이관 리스크 분석

> **v1.0 (2026-08-19)** · 검토 근거 문서: `fieldcheck/DESIGN.md`(§4 장비·§8 자동 실행·§10 이관
> 원칙), 실서비스 저장소 `docs/migration/decisions-2026-07-06.md`(이관 확정 결정)·
> `api-contract.md`(FieldCheck 엔드포인트 등재 방식), `fieldvoice/DESIGN.md`
>
> **전제**: FieldCheck가 ThinQ Real 전용 노트북(팀원 기증 개인 유휴 PC, **사내 보안 프로그램
> 미설치**)으로 이전 예정이고, FieldVoice도 같은 장비에서 동작한다고 가정한다.
> ThinQ Real 시스템 전체의 사내 이관(thinqreal.lge.com, 단일 컨테이너→EKS)이 병행 중이다.

## 0. 결론 요약

공용 운영 자체는 **시간대가 상보적이라 성립**한다(FieldCheck=슬롯 회피·아침 점검,
FieldVoice=슬롯 중 녹음). 실질 리스크는 기기 경합이 아니라 **③계정 의존, ④개인정보 통제,
⑦이관 정합** 세 가지이며, 셋 다 지금 결정해 두면 이관 시점에 비용이 거의 없다.
가장 급한 결정 1개: **공용 장비에 개인 Claude 계정을 상주 로그인시킬 것인가** (R2).

## 1. 리스크 매트릭스

### R1. 자원 경합 (오디오·CPU) — 낮음, 운영 수칙으로 해소

| 자원 | FieldCheck | FieldVoice | 충돌 |
|---|---|---|---|
| 마이크 | 내장 마이크 (07:00 점검 + 슬롯 회피) | 별도 USB 무선 수신기 (슬롯 중) | 장치 분리 + 시간 분리 — 없음 |
| 스피커 | 점검 발화 재생 | 사용 안 함 | 없음 |
| CPU | 점검 수 분 (07:00) | **전사 medium = 수 시간** (임의 시점) | ⚠ 겹치면 FieldCheck 응답 시간 측정 왜곡 |

- **문제**: FieldVoice 전사가 07:00 점검과 겹치면 CPU 포화로 FieldCheck의 `latency_ms`
  (응답 시작 시간)가 오염된다 — 시나리오별 기준선 데이터(처리 경로의 지문)가 훼손됨.
- **개선**: ① 운영 수칙 — 전사는 시연 종료 후(16:30~) 걸어두고 퇴근, 다음 날 아침 확인
  ② (백로그) 파이프라인에 "점검 금지 창(06:30~08:00) 자동 대기" 옵션 ③ 전사 프로세스
  저우선순위 실행(nice/우선순위 낮음)

### R2. 개인 Claude 계정 의존 — **중~높음, 이 문서의 핵심 결정 사항**

> 접근 통제 확인 (2026-08-19 사용자): 이 장비의 사용 권한자는 **ThinQ Real 관리자 3인뿐**
> (강원석 포함). 따라서 '불특정 접근' 시나리오는 제외하고 아래를 평가한다.

현재 FieldVoice 분석 백엔드(claude_cli)는 Claude Code 로그인이 필요하다. 공용 노트북에
**개인(강원석) 계정을 상주 로그인**시키면:

1. **자격 증명 공유**: 관리자 3인 한정이라 악용 위험은 낮지만, 다른 2인이 개인 계정
   세션을 (의도치 않게라도) 쓸 수 있는 구조 — 계정 활동의 귀속이 불분명해짐.
   또한 장비가 방문객이 드나드는 쇼룸에 상주하므로 **도난 시나리오는 인원 통제와 별개**
2. **구독 사용량 전용(轉用)**: 팀 장비의 분석이 개인 Max 구독 한도를 소모 — 사용량 충돌
   (개인 작업이 한도에 걸림) + 비용 부담 주체 불일치. 3인이 쓰는 장비일수록 심화
3. **이관 불가 요소**: 개인 계정은 인수인계가 원리적으로 불가능 — "강원석이 없으면 안
   도는 시스템"은 FieldCheck가 처음부터 피해온 설계(§10 인증 분리 원칙)와 정면 충돌

**개선 로드맵 (단계별)**:

| 시기 | 방안 | 근거 |
|---|---|---|
| **지금 (파일럿)** | 분석은 **개인 맥북에서** 수행 유지 — 공용 노트북은 녹음·(선택)전사까지만. 전사 텍스트를 맥북으로 옮겨 분석 | 개인 계정을 공용 장비에 안 올리는 가장 간단한 분리. 전사 .txt는 가볍고 옮기기 쉬움 |
| 중기 | **사내 Claude Code 사용 신청** — 이관 회의 액션 아이템 #8("사내 클로드 코드 사용 신청 절차 확인, 담당: 강원석")과 동일 트랙. 승인되면 공용 장비에 사내 계정으로 로그인 | 이미 회사가 절차를 진행 중인 경로. `llm_backend` 추상화 덕에 코드 수정 0 |
| 대안 | 회사 API 계정(크레딧) — `llm_backend: api` + 키를 config(비커밋)로 | 계정 독립적. 과금 승인 필요 |
| **이관 후** | 사내 승인 LLM/API로 교체 — `agents.py`의 백엔드 추상화가 교체 지점 | 백엔드 이원화(2026-08-19 구현)가 이관 게이트를 미리 만든 셈 |

### R3. 개인정보 통제 약화 — 중간(3인 통제 확인으로 하향), 즉시 조치 가능

DESIGN.md §5의 "원본 음성은 로컬 보관"이 전제한 '통제된 로컬'은 **개인이 관리하는 잠긴
장비**였다. 사용 권한이 관리자 3인으로 통제됨이 확인되어(2026-08-19) 내부자 위험은
낮게 보나, **장비가 방문객 출입 공간(쇼룸)에 상주**하고 보안 프로그램이 없으므로
도난·분실 시나리오에 대한 대비(특히 디스크 암호화)는 여전히 필요하다.

**즉시 조치 (노트북 셋업 시 함께)**:
1. **디스크 전체 암호화** — Windows면 BitLocker, Mac이면 FileVault (기증 PC 셋업 1순위)
2. **로그인 암호 + 자동 잠금** (FieldCheck 상시 가동 설정과 병행 — 화면 잠금은 점검
   프로그램 동작에 지장 없음, 로그온 세션만 유지되면 됨)
3. **운영 전용 로컬 계정** 사용 — 개인 계정과 분리
4. **보관 최소화**: 전사 검수 후 원본 음성 즉시 파기(§5의 30일보다 짧게 운영), (백로그)
   `--purge-days` 자동 정리 옵션
5. 관리자 페이지 업로드는 가명화 1페이지 요약만 (§8 원칙 — 이미 설계에 반영)

### R4. Git·GitHub 인증 — 중간

공용 노트북의 저장소 클론에 개인 GitHub 인증(PAT)이 상주하면 R2와 같은 구조의 문제.
- **개선**: 공개 저장소라 **읽기 전용(clone/pull)은 인증 불필요** — 공용 장비는 pull만
  하고 push는 개인 장비에서. 코드 수정이 공용 장비에서 필요해지면 그때 deploy key(읽기
  전용) 검토. 이관 후에는 사내 GitHub Enterprise로 remote 교체(이관 결정 §②).

### R5. OS 차이 — 중간, 착수 전 확인 1개

기증 PC의 OS 확인이 선행 조건. **Windows일 가능성이 높고, FieldCheck에는 Windows가
오히려 유리**하다(맥 TCC 마이크·카메라 권한 함정 해소, 웹캠 수동 노출 고정 가능 —
fieldcheck DESIGN §5·§8). FieldVoice 쪽 영향:
- `run.sh`는 bash 전용 → **Windows용 `run.bat`(또는 ps1) 필요** (백로그, 소규모)
- faster-whisper·Flask·anthropic은 Windows 동작에 문제 없음
- Claude Code CLI의 Windows 지원 확인 필요 (R2 결정에 따라 불필요할 수도)
- 인텔 CPU 성능에 따라 medium 전사 시간 재실측 필요

### R6. 단일 장애점·운영 절차 — 중간

한 대에 두 시스템: 노트북 장애·업데이트 재부팅이 점검과 녹음을 동시에 세운다.
- FieldCheck DESIGN §4의 상시 가동 설정(절전 금지·자동 부팅·업데이트 시간대 지정)을
  셋업 체크리스트로 실행하고, **Windows 업데이트 재부팅 시간대는 두 시스템 모두의 금지
  창(07:00 점검·09:00~16:30 슬롯) 밖**으로 지정 (예: 새벽 3시)
- 역할 표를 노트북에 물리 부착: "이 장비는 ① 아침 자동 점검 ② 시연 녹음 두 가지 일을
  한다 — 끄지 말 것, 볼륨 고정" (FieldCheck 볼륨 저하 사고 선례)

### R7. 사내 이관 정합 — 세 시스템의 이관 매핑

이관 확정 결정(2026-07-06)과 대조한 변화 지점:

| 의존 요소 | 현행 | 이관 후 | FieldVoice 대응 상태 |
|---|---|---|---|
| 백엔드 API | Apps Script (`type:` 분기) | 단일 컨테이너(EKS)의 동일 계약 API | ✅ §8 설계가 endpoint·키 config 분리 전제 — 주소·키 교체만 |
| 신설 엔드포인트 등재 | — | `api-contract.md`에 존재·인증 방식 등재 (FieldCheck `health_check` 선례) | ⚠ `voc_report` 구현 시 **등재 필수** (§8 원칙 3) |
| 인증 | FV_API_KEY (Script Property) | 컨테이너 환경변수 (이관 결정 §5: 비밀값은 환경변수) | ✅ 같은 개념, 위치만 이동 |
| 관리자 화면 | thinqreal_admin.html 탭 | 동일 (컨테이너가 정적 서빙) + 사내 SSO 게이트 | ✅ 🎙 탭도 함께 이관됨. GET 토큰 게이트는 SSO로 대체 가능 |
| LLM 분석 | Claude Code CLI(개인)/API | 사내 승인 경로 (사내 Claude Code 신청 #8 또는 사내 LLM) | ⚠ R2 로드맵 — `llm_backend` 추상화가 게이트 |
| STT | 로컬 Whisper | 동일 (로컬 원칙이 이관에도 유리 — 음성이 어디에도 안 나감) | ✅ 무변경. 클라우드 STT 갈림길(§4)은 이관 후 개인정보 영향평가 대상이 되므로 **로컬 유지가 이관에도 최선** |
| 파일 전달 | 개인 Google Drive 경유 | 사내 저장소/사내망 공유 | ⚠ 이관 시 Drive 의존 제거 — 관리자 페이지 적재(§8)가 대체 경로 |
| 스케줄 | 수동 실행 | (자동화 시) K8s CronJob은 서버 측 — **녹음·전사는 현장 장비라 이관 대상 아님**. 장비는 이관 후에도 로컬 운영 | ✅ 현장 장비/서버 역할 구분 명확 |

**핵심 정합 판단**: FieldVoice는 FieldCheck §10 원칙(엔드포인트·인증·저장소의 설정 분리)을
처음부터 따랐고 백엔드 추상화도 갖췄으므로, **이관 시 교체 지점은 ① API 주소·키 ② LLM
백엔드 ③ 파일 전달 경로 세 곳뿐**이다. 세 곳 모두 config/문서에 이미 격리돼 있다.
