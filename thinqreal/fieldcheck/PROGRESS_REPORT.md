## 4. 판정 3단계 — 무엇을 잡는가

| 단계 | 묻는 것 | 방식 | 잡는 장애 | 상태 |
|------|--------|------|----------|------|
| **L1** | 말을 **했는가** | 소리 에너지만 분석 (STT 불필요, 즉시) | **7월 ATOM 장애가 정확히 이것** — 무응답 | ✅ 운영 중 |
| **L2** | **맞는** 말을 했는가 | 녹음 → 로컬 STT → 키워드 대조 | 오응답, "죄송해요 모르겠어요", 외부 연동 장애 | ✅ 운영 중 |
| **L3** | 실제로 **움직였는가** | 제어 전·후 촬영 비교 | 제어 경로 장애, 루틴 미실행 | 설계 완료 |

### L1과 L2는 무엇이 다른가
전화에 비유하면 **L1은 "전화를 받았는가", L2는 "받아서 제대로 대답했는가"**입니다.

ThinQ ON이 *"죄송해요, 잘 모르겠어요"*라고 답하면 → **L1은 통과**(소리는 났으므로), **L2는 실패**. 이 유형은 L1으로는 **원리상 잡을 수 없어서** L2가 따로 필요합니다.

반대로 무응답이면 L1 실패이고, L2는 판정하지 않습니다(할 말이 없으므로). 그래서 **L2 성공률 = "응답한 것 중 내용까지 맞은 비율"**로 읽습니다.

### 실패했을 때 원인이 갈립니다 — 3단계로 나눈 실익
- **L1 실패** → 소리 자체가 안 나옴 = **TTS 서버·네트워크·기기** (인프라 계층)
- **L2 실패** → 말은 하는데 엉뚱함 = **NLU·생성 엔진·외부 서비스 연동** (지능 계층)
- **L3 실패** → 말은 맞는데 안 움직임 = **가전 제어 경로**

날씨 질문만 L2 실패면 **AccuWeather 연동**을, 일상 대화까지 실패면 **생성 엔진 자체**를 의심합니다. 한 덩어리로 "실패"라고만 적으면 이 구분이 사라집니다.

### '응답 시작'이란 무엇인가
```
① "하이엘지" 재생  →  ② 1.5초 대기('띵' 반응)  →  ③ 점검 질문 재생
   →  ④ 재생 끝 = 0ms  ◀ 여기서부터 측정  →  ⑤ ThinQ ON 발화 시작
```
**질문을 다 말한 순간부터 답을 시작하기까지의 시간**입니다. 답변을 끝내기까지의 길이가 아닙니다.

'띵' 반응은 **일부러 측정하지 않습니다.** ATOM 장애가 *"기동어는 듣고 띵도 내지만 말을 못 하는"* 상태였기 때문에, 띵을 기준으로 삼았다면 **그 장애를 정상으로 판정**했을 것입니다.

## 5. 현장에서 발견하고 해결한 문제 5건

설계실에서는 안 나오고 **현장에서만 나온** 문제들입니다. 신뢰도의 근거이므로 남겨둡니다.

| 발견 | 문제의 본질 | 해결 |
|------|-----------|------|
| 기동어 직후 명령이 씹힘 | ThinQ ON이 '띵' 반응 전에는 못 들음 | 기동어·질문 분리 재생 + 1.5초 대기 |
| **연산 대기음('띵띵띵')을 응답으로 오판** | **TTS 장애를 정상으로 판정할 구멍** | 발성 비율 판정 — 1초 창의 70% 이상이 소리일 때만 말소리로 인정. 효과음은 간격이 있어 걸러짐 |
| 긴 답변이 다음 점검의 기동어를 씹음 | 생성형이라 답변 길이가 크게 변동 | 시나리오 사이 "조용해질 때까지 대기" — 판정 결과와 무관하게 항상 |
| 에어컨·선풍기 소음에서 정상 응답을 실패로 오판 | 절대 음량 기준이 소음 위로 잡힘 | 적응형 판정 — 음성 대역(250~4000Hz)만 측정 + **기저 소음** 자동 추정 + 기저+8dB 기준 |
| **점검 3건 전부 실패, 그런데 현장은 멀쩡** | **macOS가 마이크 권한을 조용히 거부** | 아래 별도 항목 |

### macOS 마이크 권한 함정 — 가장 위험했던 사례
자동 실행 첫날 3건 모두 실패로 기록됐습니다. **ThinQ ON은 정상이었고, 점검 장비가 소리를 못 듣고 있었습니다.**

- **원인**: macOS는 앱이 아닌 실행 파일(python)에는 마이크 권한 창을 **띄우지 않고**, 오류도 없이 **무음을 반환**합니다. 시스템 설정 목록에도 안 나타나 수동 허용조차 불가능했습니다
- **판별 단서**: 세 시나리오의 소음 측정값이 소수점까지 동일(2.4 / −32.6 dBA)하고 최고값이 기저값보다 낮음 → 보정값을 빼면 **−120dB(에너지 0)**
- **해결**: ① 정식 앱(터미널)을 경유해 실행하도록 변경 ② **무음 자동 감지** → "점검 장비 설정/권한 문제(ThinQ ON 장애 아님)"로 별도 표기 ③ `--mic-test` 진단 명령 추가

**교훈**: 점검 시스템은 **자기 자신의 고장을 스스로 진단할 수 있어야 합니다.** 그러지 못하면 자기 고장을 대상의 장애로 오보합니다. 같은 원리를 L3(카메라 미연결·렌즈 가림 감지)에도 그대로 적용할 예정입니다.

## 6. 검증 결과 (실측)

### 자동 실행 검증 — 2026-08-02 07:30
**사람 개입 없는 첫 자동 실행 성공.** 이로써 "판정이 정확한가"에 이어 **"스스로 도는가"**까지 확인됐습니다.

### L1 + L2 통합 판정 — 2026-08-01
**6건 판정 / 실패 0건** (L1 3건 + L2 3건 전원 통과)

| 시나리오 | 추정 처리 경로 | 응답 시작 | 실제 인식 결과 | 판정 |
|---|---|---|---|---|
| 시간 질문 | 기기 내 즉답 (AI 엔진 미호출) | 150 ms | "지금은 9시 33분이에요" | 통과 |
| 일상 대화 | 생성 엔진 경유 | 2,910 ms | "저는 항상 기분이 좋아요…" | 통과 |
| 날씨 | 생성 엔진 + 외부 서비스(AccuWeather) 연동 | 4,620 ms | "오늘 등천동 날씨는… 기온은 최고 34.2도…" | 통과 |

시나리오마다 기저 소음이 다르게(42.6 / 50.0 / 48.5 dBA) 측정되어 **마이크가 실제로 듣고 있음**도 함께 확인됐습니다.

### 응답 시간은 처리 경로의 지문입니다
응답 시간의 차이(150ms ≪ 2,910ms < 4,620ms)는 성능 편차가 아니라 **그 질문이 어떤 경로를 타는지를 보여줍니다.** 기기에서 바로 답하는 질문, 생성 엔진을 거치는 질문, 외부 서비스까지 다녀오는 질문의 기준선이 각각 다릅니다. 그래서:
- **시나리오별 추이**로 봐야 합니다 — "시간 질문이 3초"는 절대값으로는 정상 범위여도 이상 신호입니다
- 날씨만 느려지면 **외부 연동 경로**, 전부 느려지면 **엔진·인프라**로 지연의 위치를 특정할 수 있습니다
- L3 확장 시 **가전 단독 제어와 서비스 연동 제어의 응답 시간을 나눠 측정**해 제어 경로의 구간별 소요를 드러낼 계획입니다 — 데이터가 쌓이면 실패 전 단계인 "느려지는 중"을 조기 신호로 쓸 수 있습니다

### STT 오인식은 감수합니다 — 의도된 설계
인식 결과에 오류가 섞입니다: `사용자님`→`새형제님`, `등촌동`→`등천동`. **교정하지 않습니다.**

판정 대상은 *"질문에 맞는 답을 했는가"*이지 *"받아쓰기가 정확한가"*가 아닙니다. 위 사례 모두 기대 키워드(`날씨`·`기온`)가 살아남아 정상 통과했습니다. 대신 **기대 키워드를 여러 개 두어** 오인식 한 번이 오판정으로 이어지지 않게 했습니다.

### 판정 로직 자체 검증
**자체 시험 20건 전원 통과** — 무응답 / 순간 소음 / 연산 대기음 / 어절 쉼이 있는 말소리 / 팬 소음 / 소음 위 말소리 / 마이크 무입력 / L2 키워드 5종 / 예약 시간대 6종

| 메일에 적힌 내용 | 의미 | 첫 조치 |

| `[L1] 무응답` | ThinQ ON이 말을 안 함 | **현장에서 직접 "하이엘지" 발화** → 재현되면 TTS·네트워크 이슈 보고 |
| `[L2] 실패` + 인식 문장 표시 | 말은 했는데 내용이 다름 | 인식 문장 확인. `죄송/모르겠` 계열이면 엔진 이슈, 날씨만 실패면 **외부 연동** 의심 |
| `⚠ 점검 장비 설정/권한 문제` | **ThinQ ON 장애 아님** | 점검 장비의 마이크 권한·입력 장치 확인 (`--mic-test`) |
| `⚠ 점검 기록 없음` | 그날 한 번도 안 돌았음 | 점검 장비 전원·절전 상태 확인 |

**중요**: 실패 1건이 곧 장애는 아닙니다. **현장 재현 확인이 항상 첫 단계**입니다. 판단 근거는 녹음 파일로 남아 있습니다.

| **운영 전환** | 상주 Windows 노트북 이관 + 단일 실행파일(.exe) 패키징 + 담당자 전체 알림 전환 | 대기 |
| **Phase 2 격상** | 수동 일일 점검을 자동 점검으로 대체 — 운영자는 대시보드 확인만 | 자동·수동 병행 검증 후 |

### L3는 AI 엔진 없이 구현합니다
카메라와 쇼룸 배치가 **고정**이므로, *"이게 무엇인지 인식"*이 아니라 *"아까와 달라졌는지 비교"* 문제입니다. **관심영역의 픽셀 차이 계산으로 충분**합니다.

- 조명 켜기/끄기 → 평균 밝기 변화 · 커튼 → 변화 픽셀 비율
- 에어컨 설정온도 같은 **숫자 판독만 AI/OCR 영역**이라 초기 범위에서 제외
- **ThinQ API 상태 조회보다 카메라를 택한 이유**: API는 *"서버가 명령을 받았는가"*만 확인합니다. 명령은 접수됐는데 커튼 모터가 안 도는 경우 — **방문객 눈에 보이는 것은 물리적 변화**이고 API는 이를 잡지 못합니다

## 11. 이 시스템의 설계 원칙 (사내 이관 대비)

기존 예약 관리 시스템이 사내 이관을 준비 중이므로, FieldCheck도 **함께 이관될 것을 전제로** 설계했습니다.

1. **서버 주소는 설정 파일로 분리** — 이관 시 주소 한 줄 교체로 끝남
2. **인증은 API 키 방식** — 처음부터 키를 실어 보내는 구조
3. **데이터는 단순 행 구조** — 어떤 DB로도 옮길 수 있음
4. **판정 기준은 전부 설정값** — 코드 수정 없이 현장에서 조정 가능
5. **점검 문장은 고정 음성 파일** — 매번 새로 만들지 않음. *"오늘 실패가 ThinQ ON 문제인지 입력이 달라진 탓인지"*를 구분하려면 입력이 항상 같아야 함
