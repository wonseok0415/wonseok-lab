## 2. 시스템 개요

```
[점검 장비]  ThinQ Real 상주 노트북 + 카메라
     │  ① 저장된 음성 재생: "하이엘지" → 점검 질문·가전 제어 명령
     │  ② 내장 마이크로 응답 녹음
     │  ③ 카메라로 가전 제어 전·후 촬영
     ▼
[판정]  L1 응답 유무·시간  /  L2 내용 정확성(로컬 STT)  /  L3 물리 동작(픽셀 비교)
     ▼
[기록]  Apps Script → Google Sheets `health_checks` 탭
     ▼
[보고]  매일 아침 요약 메일  +  관리자 페이지 🩺 자동 점검 탭
```

**기존 예약 관리 시스템의 백엔드·메일 인프라를 그대로 재활용**했습니다. 신규 서버·신규 계정·신규 과금이 없습니다.

## 3. 판정 체계 — 세 가지 질문

시연 품질은 세 가지 질문으로 확인됩니다. 단계마다 보는 계층이 다르고, **어느 단계에서 실패했는지가 곧 원인 진단**입니다.

| 단계 | 묻는 것 | 방식 | 잡는 장애 |
|------|--------|------|----------|
| **L1** | 말을 **했는가** | 소리 에너지 분석 (STT 불필요, 즉시) | **7월 ATOM 장애가 정확히 이것** — 무응답 |
| **L2** | **맞는** 말을 했는가 | 녹음 → 로컬 STT → 키워드 대조 | 오응답, "죄송해요 모르겠어요", 외부 연동 장애 |
| **L3** | 실제로 **움직였는가** | 명령 전·후 카메라 촬영 픽셀 비교 | 가전 제어 경로 장애, 루틴 미실행 |

### 실패 지점이 곧 원인 계층
- **L1 실패** → 소리 자체가 안 나옴 = **TTS 서버·네트워크·기기** (인프라 계층)
- **L2 실패** → 말은 하는데 엉뚱함 = **NLU·생성 엔진·외부 서비스 연동** (지능 계층)
- **L3 실패** → 말은 맞는데 안 움직임 = **가전 제어 경로**

날씨 질문만 L2 실패면 **AccuWeather 연동**을, 일상 대화까지 실패면 **생성 엔진 자체**를 의심합니다. 한 덩어리로 "실패"라고만 적으면 이 구분이 사라집니다.

### L1과 L2는 무엇이 다른가
전화에 비유하면 **L1은 "전화를 받았는가", L2는 "받아서 제대로 대답했는가"**입니다. ThinQ ON이 *"죄송해요, 잘 모르겠어요"*라고 답하면 → L1 통과(소리는 났으므로), **L2 실패**. 이 유형은 L1으로는 **원리상 잡을 수 없어서** L2가 따로 필요합니다.

무응답이면 L1 실패이고 L2는 판정하지 않습니다(할 말이 없으므로). 그래서 **L2 성공률 = "응답한 것 중 내용까지 맞은 비율"**로 읽습니다. L3도 같은 원리로, 명령이 접수된 건에서 물리 동작을 봅니다.

## 4. 판정 원리 — L1 (응답 감지)

### '응답 시작'이란
```
① "하이엘지" 재생  →  ② 1.5초 대기('띵' 반응)  →  ③ 점검 질문 재생
   →  ④ 재생 끝 = 0ms  ◀ 여기서부터 측정  →  ⑤ ThinQ ON 발화 시작
```
**질문을 다 말한 순간부터 답을 시작하기까지의 시간**입니다. 답변을 끝내기까지의 길이가 아닙니다.

'띵' 반응은 **일부러 측정하지 않습니다.** ATOM 장애가 *"기동어는 듣고 띵도 내지만 말을 못 하는"* 상태였기 때문에, 띵을 기준으로 삼았다면 **그 장애를 정상으로 판정**했을 것입니다.

### 소리에서 '말'을 가려내는 3겹 필터
쇼룸에는 에어컨·선풍기 소음과 ThinQ ON 자신의 효과음('띵')이 섞여 있습니다. 녹음에서 **ThinQ ON의 목소리만** 가려내기 위해 세 겹의 필터를 통과시킵니다.

| 단계 | 기법 | 무엇을 걸러내는가 |
|------|------|------------------|
| ① 대역 필터 | 사람 목소리 대역(**250~4,000Hz**)의 에너지만 측정 | 에어컨·선풍기의 **저주파 팬 소음** — 아무리 커도 측정에서 제외 |
| ② 기저 소음 자동 추정 | 녹음마다 조용한 하위 10% 구간을 그날의 **기저 소음**으로 잡고, 기저 **+8dB 이상**만 발성 후보로 인정 | 그날그날 다른 **배경 소음 수준** — 고정 기준이 아니라서 소음 환경이 바뀌어도 재보정 불필요 |
| ③ 발성 비율 판정 | 1초 구간의 **70% 이상**이 발성 프레임일 때만 '말'로 인정 | **'띵' 효과음**(짧은 소리+간격 반복 → 비율 미달)과 문 닫힘 같은 **순간 소음**. 어절 사이 쉼이 있는 말소리는 통과 |

③이 특히 중요합니다 — *"연산음('띵띵띵')은 내는데 말을 못 하는"* 상태를 단순히 "소리가 났는가"로 판정하면 정상으로 오판합니다. 세 필터를 모두 통과한 최초 시점이 '응답 시작'으로 기록됩니다. 판정에 AI가 없습니다 — 전부 신호 처리(산술)라 결과가 재현 가능하고 빠릅니다.

## 5. 판정 원리 — L2 (음성 인식과 키워드 판정)

L2는 2단 구조입니다: **받아쓰기는 STT 엔진이, 판정은 키워드 규칙이** 합니다.

### 채택 엔진 — Whisper (OpenAI, 오픈소스)
- 2022년 공개된 음성 인식(STT) AI 모델 — 68만 시간 다국어 음성으로 학습(한국어 포함), 무료
- 대화형 AI가 아니라 **'받아쓰기'만 하는 모델** — 녹음을 넣으면 문장이 나옴
- **점검 장비 노트북 안에서 실행** (small 모델 약 500MB, CPU 동작)

**로컬 실행이 핵심**입니다: ① 공간의 음성이 외부로 나가지 않아 **보안 검토 부담이 없고** ② 인터넷이 끊겨도 판정이 계속되며(정작 장애 상황에서 점검이 멈추는 구조를 회피) ③ 계정·과금이 없습니다.

### 판정 흐름
```
① 응답 녹음(WAV) → ② STT 전사: "오늘 등천동 날씨는… 기온은 최고 34.2도…"
→ ③ 키워드 판정: 회피 표현(죄송/모르겠/찾지 못했…) 있으면 실패 → 기대 키워드(날씨/기온…) 있으면 통과
→ ④ 결과 + 인식 문장을 시트에 기록 (실패 시 메일에 인식 문장 표시)
```
STT는 받아쓰기까지만 하고, **판정 자체는 단순 키워드 규칙**입니다. AI의 판단이 아니라 규칙이므로 같은 녹음에는 항상 같은 결과가 나오고(재현 가능), 왜 실패인지 설명할 수 있습니다.

### 받아쓰기 오류는 감수합니다 — 의도된 설계
`등촌동`→`등천동` 같은 오인식이 섞여도 **교정하지 않습니다.** 판정 대상은 *"질문에 맞는 답을 했는가"*이지 *"받아쓰기가 정확한가"*가 아니며, **기대 키워드를 여러 개** 두어 오인식 한 번이 오판정으로 이어지지 않게 했습니다.

## 6. 판정 원리 — L3 (물리 동작 검증)

### 왜 카메라인가, 왜 AI가 없는가
- **API 상태 조회 대신 카메라**: API는 *"서버가 명령을 받았는가"*까지만 알려줍니다. 명령은 접수됐는데 커튼 모터가 돌지 않는 경우 — **방문객 눈에 보이는 것은 물리적 변화**이고, 시연 품질을 지키려면 그것을 봐야 합니다.
- **AI 영상 인식 없이 산수만으로**: 카메라와 쇼룸 배치가 고정이라 *"무엇인지 인식"*이 아니라 *"아까와 달라졌는지 비교"* 문제입니다. 사각형 두 영역의 평균 밝기 비교 — 더하기와 나누기면 충분하고, 그래서 검증·설명·재현이 가능합니다.

### 판정 지표 — 두 영역의 밝기 '상대값'
카메라 화면에서 사각형 두 개만 봅니다: **대상 영역**(조명 기구)과 **참조 영역**(변하지 않는 벽). 매초 두 영역의 평균 밝기(픽셀값 0~255)를 계산하고, 지표는 **상대값 = 대상 밝기 ÷ 참조 밝기**입니다.

절대 밝기가 아니라 비율을 쓰는 이유는 **카메라 자동 노출** 때문입니다 — 조명이 켜지면 카메라가 스스로 노출을 낮춰 화면 전체가 도로 어두워지므로, 절대 밝기로는 "켜졌는데 변화 없음"으로 오판합니다. 두 영역이 같은 노출을 공유하므로 비율에서는 이 왜곡이 상쇄됩니다.

#### 실측 계산 예 (ThinQ Real 현장)
- 한 표본의 계산: 대상 **74.5** ÷ 참조 **78.3** = 상대값 **0.951**

| 상태 (실측) | 상대값 |
|---|---|
| 조명 꺼짐 | **0.746** |
| 조명 켜짐 | **1.063** |

### 판정 기준 — '명령 직후의 변화량'
**명령 직후 60초 안에 상대값이 0.15 이상 변했는가(|Δ|≥0.15)** 하나입니다. 위 실측이면 |1.063 − 0.746| = **0.317 ≥ 0.15 → "동작함"** — 실측 변화폭이 기준의 2배라 여유가 충분합니다.

절대값("얼마나 밝은가")이 아니라 변화량을 쓰는 근거는 **시간 구조**입니다. 채광(햇빛·구름·커튼)은 천천히 변하지만 가전은 명령 직후에 급변합니다. 그래서 절대 밝기의 기준선은 시각·날씨에 따라 떠다녀도 "명령 직후의 큰 변화"는 가전의 반응으로 판정할 수 있고 — 무인 점검에는 조명을 만질 사람도 없습니다 — 시각마다 임계값을 다시 잴 필요가 없습니다. 변화가 시작되기까지의 시간은 **가전 반응 시간**으로 기록되어 L1 '응답 시작'의 물리 동작판 지표가 됩니다.

### 점검 시퀀스 — 되물음까지 흡수하는 자동 대화
① 사전 상태 촬영 → ② 기동어+명령 재생 → ③ 응답 녹음(L1·L2 판정) → ④ **무조건 확답** 재생 → ⑤ 60초 연속 촬영+녹음 → ⑥ |Δ| 판정 → 서버 전송

④가 설계 포인트입니다. ThinQ ON은 가전 명령에 *"실행할까요?"*라고 **되묻는 경우**가 있는데, 실시간 판별 대신 **항상** "응, 실행해줘"를 재생합니다 — 되물었다면 청취 모드라 접수되고, 이미 실행했다면 기동어 없는 발화라 부작용 없이 무시됩니다. 어느 쪽이든 안전한 **비대칭 구조**입니다.

### 판정 대상과 확대 순서
**조명 켜기 → 끄기 쌍**(끄기가 원상 복구 겸용 — 점검이 항상 꺼진 상태로 끝나 다음날 시작 상태가 보장됨)으로 운영을 시작해, **커튼 → 루틴(여러 가전 동시 제어)** 순으로 한 번에 한 변수씩 확대합니다. 숫자 판독이 필요한 대상(에어컨 설정온도)만 AI/OCR 영역이라 범위에서 제외합니다.

## 7. 신뢰성 설계 — 왜 이 판정을 믿을 수 있는가

### 자기 고장의 자가 진단 (3중)
점검 시스템이 자기 고장을 진단하지 못하면, **자기 고장을 ThinQ ON의 장애로 오보**합니다. 세 감각기관 모두에 자가 진단을 넣었습니다.

| 감각 | 고장 모드 | 자가 진단 |
|------|----------|----------|
| **마이크** (듣기) | 권한 거부 시 OS가 오류 없이 무음 반환 | 완전 무음(에너지 0) 감지 → "점검 장비 설정/권한 문제" 표기 + 진단 명령 |

세 경우 모두 실패가 **"ThinQ ON 장애 아님"으로 구분 표기**되어, 아침 메일에서 기기 장애와 장비 문제가 섞이지 않습니다.

### 오판을 막는 운영 장치
- **증거 보존**: 응답 녹음·확답 이후 녹음·판정 시점 스냅샷을 전부 저장 — 판정에 의문이 생기면 언제든 원본을 다시 보고 들을 수 있습니다
- **입력 재현성**: 점검 음성은 한 번 만든 WAV로 고정 — 매번 같은 입력이어야 "오늘 실패 = ThinQ ON 쪽 변화"라고 말할 수 있습니다
- **예약 시간대 자동 회피**: 발화 전 예약 시스템을 조회해 확정 예약·차단 슬롯(시작 20분 전~종료 10분 후)에는 점검하지 않음 — 시연 중 스피커가 말을 거는 사고 방지. 조회 실패 시에도 건너뜀(안전 우선)

### 응답 시간은 처리 경로의 지문입니다

| 시나리오 | 추정 처리 경로 | 응답 시작 | 실제 인식 결과 |
|---|---|---|---|
| 시간 질문 | 기기 내 즉답 (AI 엔진 미호출) | 150 ms | "지금은 9시 33분이에요" |
| 일상 대화 | 생성 엔진 경유 | 2,910 ms | "저는 항상 기분이 좋아요…" |
| 날씨 | 생성 엔진 + 외부 서비스(AccuWeather) 연동 | 4,620 ms | "오늘 등천동 날씨는… 34.2도…" |

응답 시간의 차이는 성능 편차가 아니라 **그 질문이 어떤 경로를 타는지**를 보여줍니다. 시나리오별 추이로 보면 — 날씨만 느려지면 외부 연동 경로, 전부 느려지면 엔진·인프라로 **지연의 위치를 특정**할 수 있고, 데이터가 쌓이면 실패 전 단계인 "느려지는 중"을 조기 신호로 쓸 수 있습니다. L3의 가전 반응 시간도 같은 원리로, 가전 단독 제어와 루틴(연동) 제어의 경로 차이를 드러낼 원자료입니다.
