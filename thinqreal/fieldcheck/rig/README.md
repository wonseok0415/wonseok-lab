# FieldCheck 점검 장비 — 노트북 설치 가이드

> 처음 해보는 사람 기준으로 쓴 가이드입니다. 순서대로 따라 하면 됩니다.
> 이 프로그램이 하는 일: **오늘 예약이 있는지 확인 → 저장된 점검 음성을 스피커로 재생 → ThinQ ON의 응답을 마이크로 녹음 → ① 응답이 왔는지·몇 초 걸렸는지(L1) ② 내용이 맞는지(L2) 자동 판정 → 결과를 Google Sheets에 기록, 매일 아침 요약 메일.**
>
> **Windows와 맥 모두 지원**합니다. 최초 점검(개발자 작업 PC = 맥북)은 아래 [맥에서 실행하기]를 참고하고, 상주 장비(Windows 노트북)는 본문 순서대로 진행하세요.

## 판정 단계

| 단계 | 무엇을 보는가 | 어떻게 |
|------|--------------|--------|
| **L1** | 말을 했는가 / 답을 시작하기까지 얼마나 걸렸는가 | 녹음의 A-가중 음성 대역 레벨 + 발성 비율 (2026-07 ATOM TTS 장애가 이 단계에서 잡힘) |
| **L2** | 내용이 맞는가 | 로컬 STT(Whisper)로 텍스트화 → 기대 키워드 / 회피 표현 검사 |
| L3 | 가전이 실제 동작했는가 | 웹캠 전후 이미지 비교 (미구현 — Phase 2) |

**L2는 L1을 통과한 건에 대해서만 판정**합니다. 응답 자체가 없으면 판정할 말이 없고, 같은 실패를 두 건으로 세면 통계가 왜곡되기 때문입니다. 따라서 요약 메일의 L2 성공률은 "응답한 것 중 내용까지 맞은 비율"로 읽으면 됩니다.

L2의 핵심 가치는 **회피 표현 감지**입니다. ThinQ ON이 "죄송해요, 잘 모르겠어요"라고 답하면 L1은 통과(소리는 났으므로)하지만 실제로는 실패입니다. 이 유형은 L1으로는 원리상 잡을 수 없습니다.

### '응답 시작'(latency_ms)이 재는 것

점검 한 회차는 이런 순서로 진행됩니다:

```
① "하이 엘지" 재생  →  ② ThinQ ON '띵'  →  ③ 1.5초 대기  →  ④ 점검 질문 재생
                                                                    ↓ 재생 끝 = 0ms 기준점
                                                              ⑤ 녹음 시작 ────── ⑥ ThinQ ON이 말을 시작 = 응답 시작
```

**④가 끝난 순간부터 ⑥까지**의 시간입니다. 즉 **"질문을 다 말한 뒤 답이 나오기 시작할 때까지"**입니다.

- ✗ 기동어 '띵' 시점부터가 **아닙니다** (기동어·질문 재생은 녹음 전에 끝납니다)
- ✗ 답변을 **끝내기까지**의 길이가 아닙니다 (생성형 답변은 길이가 매번 달라 지표로 부적합)

L1이 보는 것은 "답을 시작했는가"이므로 이 값이 맞는 지표입니다. 이 값이 갑자기 커지면 ThinQ ON 서버 응답이 느려지고 있다는 조기 신호로 읽을 수 있습니다.

## 2. 필요 프로그램 설치 (딱 한 번)

명령 프롬프트에서 이 폴더로 이동한 뒤 설치:
```
cd C:\fieldcheck\rig        ← 실제 복사해 둔 경로로
pip install sounddevice numpy
pip install faster-whisper          ← L2(내용 판정)용. 생략하면 L1만 동작
```
- `faster-whisper`는 **음성 인식을 이 노트북 안에서** 처리합니다. 공간의 음성이 외부로 나가지 않고, 사용료도 없으며, 인터넷이 끊겨도 판정됩니다.
- ⚠ **첫 실행 시 모델 파일(약 500MB, `small` 기준)을 인터넷에서 한 번 내려받습니다.** 이후에는 캐시를 재사용하므로 인터넷이 필요 없습니다. 점검 장비를 설치할 곳의 네트워크가 제한적이라면, **인터넷이 되는 곳에서 `--transcribe`를 한 번 실행해 모델 캐시를 만든 뒤** 점검 장비로 옮기세요.
- 설치하지 않아도 프로그램은 정상 동작하며, L2만 조용히 건너뜁니다.

## 3. 설정 파일 만들기 (딱 한 번)

1. `config.example.json`을 복사해서 같은 폴더에 `config.json`으로 저장
2. 메모장으로 열어 두 값 확인:
   - `endpoint_url` — Apps Script **메인 배포 주소** (예시 파일의 기본값이 현재 운영 주소). 예약 조회나 결과 전송이 **404**로 실패하면 이 값이 폐기된 배포 주소인 경우가 대부분 — 예시 파일의 주소로 교체할 것
   - `api_key` — Apps Script **Script Property `FC_API_KEY`에 등록된 값**과 같아야 함 (프로젝트 설정 → 스크립트 속성). 예시 파일의 자리표시자를 실제 값으로 바꿔야 동작하며, 키가 다르면 서버가 전송을 전부 거부함(Unauthorized)
   - ⚠ 실제 키는 `config.json`(커밋 금지)에만 둘 것 — 코드·예시 파일·문서에 적으면 안 됨 (초기 키 `fieldcheck2026`은 노출로 폐기됨)

> **이미 `config.json`을 쓰고 있는데 프로그램이 업데이트된 경우**는 손으로 고치지 말고 아래 명령을 쓰세요. **새로 생긴 항목만** 채우고 기존 값(보정값·장치 번호·키워드)은 그대로 둡니다. 이전 파일은 `config.json.bak`으로 백업됩니다.
> ```
> python fieldcheck.py --upgrade-config
> ```

## 4. 점검 음성 만들기 (딱 한 번)

Windows 내장 음성합성으로 점검 문장을 WAV 파일로 만듭니다:
```
python synthesize_phrases.py "하이 엘지" phrases/wake.wav
python synthesize_phrases.py "지금 몇 시야?" phrases/ask_time.wav
python synthesize_phrases.py "오늘 기분 어때?" phrases/smalltalk.wav
python synthesize_phrases.py "오늘 날씨 어때?" phrases/ask_weather.wav
```
- 기동어("하이 엘지" 부분)는 **실제 ThinQ ON 기동어**로 바꿔서 만드세요.
- **명령 문장 앞에 기동어를 붙이지 마세요.** 프로그램이 기동어 파일을 먼저 재생하고, ThinQ ON이 '띵' 하고 반응할 시간(`wake_gap_seconds`, 기본 1.2초)을 기다린 뒤 명령을 재생합니다. 명령이 앞부분부터 씹히면 이 값을 1.5~2.0으로 올려보세요 (config.json).
- 합성 음성을 ThinQ ON이 인식하지 못하면: Windows **녹음기 앱**으로 사람 목소리를 직접 녹음해서 같은 파일명(`phrases/wake.wav` 등)으로 저장하면 됩니다.
- **중요**: 한 번 만든 파일은 바꾸지 마세요. 매번 같은 음성이 재생되어야 "오늘 실패가 ThinQ ON 문제"라고 말할 수 있습니다.

## 6. 첫 점검 실행

```
python fieldcheck.py --once
```
- 스피커에서 점검 음성이 나오고, ThinQ ON이 대답하면 `[OK ]`, 무응답이면 `[FAIL]`이 표시됩니다.
- 결과는 Google Sheets `health_checks` 탭에 자동 기록됩니다.
- 기동어 인식이 안 되면: 노트북 **볼륨을 조금씩 올리며** `--once`를 반복 → 잘 되는 볼륨을 찾은 뒤 **그 볼륨으로 고정** (이후 변경 금지)

## 7. 주기 점검 시작

```
python fieldcheck.py --loop
```
- `config.json`의 `loop_interval_minutes`(기본 30분) 간격으로 자동 반복합니다.
- `active_hours`(기본 07:00–19:00) 밖의 시간에는 발화하지 않습니다.
- 창을 닫으면 중지됩니다. 상시 운영 시에는 창을 열어 둔 채 노트북 덮개만 닫으세요 (아래 8번 설정 필수).

1. 설정 → 시스템 → 전원: "덮개를 닫으면" → **아무 것도 안 함**
2. 같은 화면에서: 전원 연결 시 절전 모드 → **안 함**

## 9. 매일 자동 실행 (중요)

`--once`는 사람이 명령을 칠 때만 돕니다. 노트북을 켜 두어도 **정해진 시각에 스스로 실행되지는 않습니다.** 실제로 2026-08-01 아침 요약이 "⚠ 점검 기록 없음"으로 온 이유가 이것입니다.

기본 실행 시각은 **매일 07:00** — 점검이 끝난 뒤 07:40 무렵 요약 메일이 발송되고, 사내 메일 게이트웨이 지연을 감안해도 09:00 1회차 시연 전에 받아볼 수 있습니다.

**맥 (개발·검증용)**
```
cd ~/workspace/wonseok-lab/thinqreal/fieldcheck/rig
bash schedule/install_macos.sh            # 매일 07:00 (시각 변경: install_macos.sh 8 15)
```
설치 후 **반드시 한 번 수동 실행**해서 마이크 권한을 승인해야 합니다. 승인 전에는 **오류 없이 조용히 무음만 녹음하며 매일 실패**합니다.
```
launchctl kickstart -p gui/$(id -u)/com.thinqreal.fieldcheck
```
새 터미널 창이 열리면서 점검이 실행되고, **"터미널이(가) 마이크에 접근하려고 합니다"** 창이 뜹니다. **[허용]**을 누르세요. 한 번만 하면 이후 계속 유지됩니다.

> **왜 터미널을 거쳐 실행하나요?** (2026-08-01 현장 확인)
> launchd가 `python3`을 직접 실행하면 macOS가 마이크 권한 창을 **띄우지 않습니다.** 앱 번들이 아닌 실행 파일은 개인정보 보호(TCC) 대상으로 인정되지 않아, 묻지도 않고 무음을 돌려줍니다. 시스템 설정의 마이크 목록에도 나타나지 않아 수동으로 켤 수도 없습니다.
> 그래서 정식 앱인 **터미널을 통해** 실행합니다. 터미널은 권한 창이 정상적으로 뜨고, 매일 아침 창이 열리며 진행 상황이 눈에 보이는 부수 효과도 있습니다.

등록 직후 **"로그인 항목 및 확장 프로그램"** 창이 뜨는 것은 정상입니다. macOS가 "백그라운드 항목이 추가됐다"고 알리는 것으로, **스위치가 켜져 있는지만 확인**하면 됩니다 (별도로 실행할 것은 없습니다).

권한이 제대로 들어갔는지 확인:
```
python3 fieldcheck.py --mic-test
tail -f logs/schedule.log        # 자동 실행 결과 확인 (Ctrl+C로 빠져나옴)
```
그 시각에 맥이 잠들어 있으면 실행되지 않으므로, 자동 기상도 함께 설정합니다 (관리자 암호 필요):
```
sudo pmset repeat wakeorpoweron MTWRFSU 07:25:00
```
해제: `bash schedule/uninstall_macos.sh`

**Windows (상주 장비)**
```
powershell -ExecutionPolicy Bypass -File schedule\install_windows.ps1
```
절전 중이면 깨워서 실행(`WakeToRun`), 그 시각을 놓쳤으면 이후에라도 실행(`StartWhenAvailable`)하도록 등록됩니다. 스피커·마이크를 쓰므로 **로그온 상태**여야 하며, 덮개만 닫아 두는 운영 방식은 위 8번 설정과 함께 사용합니다.

> **자동 실행이 잘 되고 있는지 확인하는 법**: 매일 아침 요약 메일이 "점검 기록 없음"이 아니면 정상입니다. 이 메일 자체가 점검 장비 생존 확인 장치입니다.

## 예약 시간대 자동 회피

점검 장비는 **소리를 내어** 말을 겁니다. 방문객 시연 중에 점검 발화가 나가면 시연을 방해하므로, 발화 직전에 예약 관리 시스템에 오늘 예약을 물어보고 예약 시간대에는 건너뜁니다.

- 조회: `GET {endpoint_url}?type=availability&date=오늘` → 확정 슬롯 / 관리자 차단 슬롯
- 회피 대상: **확정 예약** + **관리자 차단 슬롯**(운영 사정상 예약 불가 — 촬영 등). 대기중 예약은 기본적으로 회피하지 않음
- 여유 시간: 슬롯 시작 **20분 전**부터 종료 **10분 후**까지 (방문객이 일찍 오거나 늦게 나가는 경우 대비)

`config.json`의 `booking_avoidance`로 조정합니다:

| 키 | 기본값 | 의미 |
|----|--------|------|
| `enabled` | `true` | 회피 기능 on/off |
| `guard_before_minutes` | `20` | 슬롯 시작 몇 분 전부터 회피 |
| `guard_after_minutes` | `10` | 슬롯 종료 몇 분 후까지 회피 |
| `avoid_blocked` | `true` | 관리자 차단 슬롯도 회피 |
| `avoid_pending` | `false` | 대기중(미확정) 예약도 회피 |
| `on_query_failure` | `"skip"` | 조회 실패 시 동작 (`skip` = 건너뜀 / `proceed` = 진행) |
| `slot_windows` | 1·2·3회차 | 슬롯 번호별 시간대 (예약 시간표가 바뀌면 여기만 수정) |

> **조회에 실패하면 왜 건너뛰나요?** 같은 날 조회에 성공한 적이 있으면 그 결과를 재사용하고, 그것도 없으면 건너뜁니다. "예약이 있는지 모르는 상태"에서 스피커로 말을 거는 위험(시연 방해)이, 점검 한 회차를 거르는 손실보다 크다고 보기 때문입니다. 반대 정책이 필요하면 `on_query_failure`를 `"proceed"`로 바꾸세요.

수동으로 지금 당장 점검해야 한다면 `--force`를 붙입니다 (**시연 중이 아닌지 직접 확인 후** 사용):
```
python fieldcheck.py --once --force
```

## L2 내용 판정 조정

시나리오마다 기대하는 답이 다르므로 `config.json`의 시나리오에 키워드를 넣습니다.

| 키 | 의미 |
|----|------|
| `expect_any` | 이 중 **하나라도** 있으면 통과 (예: 날씨 질문 → `["날씨","기온","맑",...]`) |
| `expect_all` | **전부** 있어야 통과 |
| (둘 다 없음) | 자유 대화로 보고 **최소 길이**(`stt.min_chars`, 기본 4자)만 확인 |
| `forbid_any` | 하나라도 있으면 **실패** (해당 시나리오만. 생략하면 아래 공통값 사용) |

공통 회피 표현은 `stt.forbid_any_default`에 있습니다 — `모르겠 / 죄송 / 다시 말씀 / 이해하지 못 / 지원하지 않 / 확인할 수 없 / 알 수 없`. ThinQ ON이 이런 말을 하면 소리는 났어도 질문을 처리하지 못한 것이므로 실패로 봅니다.

**키워드는 실제 녹음으로 다듬으세요.** 발화 없이 이미 저장된 녹음만으로 판정을 시험할 수 있습니다:
```
python fieldcheck.py --transcribe 20260731_065245_l1_weather.wav
python fieldcheck.py --transcribe recordings/어떤파일.wav --scenario l1_weather
```
(파일명이 `..._시나리오ID.wav` 형식이면 시나리오는 자동으로 찾습니다.)

`stt` 설정:

| 키 | 기본값 | 의미 |
|----|--------|------|
| `enabled` | `true` | L2 판정 on/off |
| `engine` | `"auto"` | `faster-whisper` → `openai-whisper` 순으로 사용 가능한 것 선택 |
| `model` | `"small"` | 클수록 정확하고 느림 (`tiny`/`base`/`small`/`medium`). 오래된 노트북에서 느리면 `base`로 |
| `language` | `"ko"` | 인식 언어 |
| `min_chars` | `4` | 자유 대화 시나리오의 최소 응답 길이 |
| `vocabulary_hint` | 지명·제품명 목록 | Whisper에게 "이런 말이 나올 것"이라고 미리 알려주는 어휘 힌트 |

### 인식이 부정확할 때 — 어디까지 신경 써야 하나

STT는 종종 틀립니다. 실제 관측 예: `사용자님` → `새형제님`, `등촌동` → `등천동`.

**그렇다고 문장을 정확히 받아쓸 필요는 없습니다.** 우리가 판정하는 것은 "ThinQ ON이 질문에 맞는 답을 했는가"이지 "받아쓰기가 완벽한가"가 아닙니다. 위 예시도 `날씨`·`기온` 키워드가 살아 있어 정상 통과했습니다.

`expect_any`에 **동의어를 여럿 넣는 이유가 이것**입니다. 하나가 잘못 인식돼도 다른 하나가 걸리도록 하는 안전장치입니다. 키워드를 하나만 두면 오인식 한 번에 오판정이 나옵니다.

정확도를 더 올려야 한다면 비용이 낮은 순서로:
1. **`vocabulary_hint`에 자주 틀리는 단어 추가** — 지명·제품명 등 고유명사에 효과적. 비용 없음
2. **`stt.model`을 `small` → `medium`으로** — 약 1.5GB, 인식은 좋아지고 속도는 느려짐
3. LLM으로 문맥 교정 — 외부 AI 연동이 필요하고 판정 정확도에는 거의 기여하지 않으므로 **권장하지 않음**

## 맥에서 실행하기 (최초 점검용)

맥북에서 먼저 테스트할 때는 위 1~7번 대신 이렇게 하면 됩니다:

1. **Python**: 맥에는 `python3`가 이미 있습니다. 터미널에서 `python3 --version`으로 확인 (없으면 실행 시 설치 안내가 뜹니다)
2. **설치**: 저장소 클론 후
   ```
   cd wonseok-lab/thinqreal/fieldcheck/rig
   pip3 install sounddevice numpy
   pip3 install faster-whisper        # L2(내용 판정)용 — 생략 가능
   ```
3. **한국어 음성 준비 (권장)**: 시스템 설정 → 손쉬운 사용 → 콘텐츠 말하기 → 시스템 음성 → 한국어 **Yuna** 다운로드
4. **점검 음성 생성**: Windows와 동일한 명령을 `python3`로 실행
   ```
   python3 synthesize_phrases.py "하이 엘지" phrases/wake.wav
   python3 synthesize_phrases.py "지금 몇 시야?" phrases/ask_time.wav
   python3 synthesize_phrases.py "오늘 기분 어때?" phrases/smalltalk.wav
   python3 synthesize_phrases.py "오늘 날씨 어때?" phrases/ask_weather.wav
   ```
5. **설정·소음 측정·점검**: 본문 3, 5, 6번과 동일 (`python` 대신 `python3`)
6. **마이크 권한**: 첫 녹음 시 "터미널(또는 VS Code)이 마이크에 접근하려고 합니다" 창이 뜨면 **허용**. 지나쳤다면 시스템 설정 → 개인정보 보호 및 보안 → 마이크에서 터미널/VS Code를 켜기

맥에서 만든 `phrases/*.wav`는 Windows 리그에서도 그대로 재생됩니다. 다만 **재현성 원칙**상, 상주 점검 장비를 Windows 노트북으로 옮기는 시점에 어느 파일 세트를 최종본으로 쓸지 정하고 이후에는 바꾸지 마세요.

## dBA 보정 (선택 — 숫자를 실제 소음계와 맞추기)

점검 출력의 "기저 소음 / 최고" 값은 **A-가중(dBA)** 측정입니다. 다만 노트북 마이크는 교정된 소음계가 아니라서, 보정 전에는 **상대값**으로 표시됩니다 (판정 정확도에는 영향 없음 — 판정은 기저 소음 대비 차이만 사용).

> **원리**: 휴대폰 앱 값과 점검 장비 값은 **둘 다 A-가중이 적용된** dB입니다. 차이는 기준점뿐 —
> 앱은 음압(20µPa) 기준, 점검 장비는 마이크 신호의 디지털 최대치 기준. dB는 비율 단위라
> 기준점 차이는 상수 하나로 환산되며, 아래 4번의 뺄셈이 그 상수를 구하는 과정입니다
> (실제 소음계의 1점 교정과 같은 원리). 마이크 특성·대역 제한 때문에 ±수 dB 오차가
> 있는 근사치이며, 판정은 보정과 무관하게 동작합니다.

실제 소음계 숫자처럼 보고 싶으면 한 번만 보정하세요:

1. 휴대폰에 소음측정 앱 설치 (예: "Sound Meter", 데시벨 측정기)
2. `python3 fieldcheck.py --calibrate` 실행 — 표시값 확인 (예: `-38.2 dBA (상대값)`)
3. 같은 자리·같은 시점에 휴대폰 앱으로 측정 (예: `47 dBA`)
4. `config.json`에 차이를 입력: `"dba_calibration_offset": 85.2` ← 47 − (−38.2)
5. 이후 모든 출력·기록이 실측 근사 dBA로 표시됩니다

## 문제 해결

| 증상 | 조치 |
|------|------|
| `python` 명령이 없다고 나옴 | Python 재설치하며 "Add to PATH" 체크 |
| 소리가 안 나옴 / 녹음이 안 됨 | `python fieldcheck.py --list-devices`로 장치 번호 확인 → `config.json`의 `output_device`/`input_device`에 번호 입력 |
| **"마이크에서 아무 소리도 들어오지 않았습니다"** | 마이크 권한 문제(볼륨과 무관). `python fieldcheck.py --mic-test`로 확인 → 맥은 시스템 설정 → 개인정보 보호 및 보안 → 마이크에서 Python 허용. 자동 실행이 무음이면 `launchctl kickstart`로 권한 창을 띄워 승인 |
| 모든 시나리오의 dBA 값이 **완전히 똑같음** | 녹음이 안 되고 있다는 신호입니다 (실제 소리는 매번 달라짐). 위 마이크 권한 항목 참고 |
| 항상 FAIL (응답하는데도) | 응답 판정은 기저 소음 대비 상대 기준(`voice_over_floor_db`, 기본 8) — 8→5로 낮추거나, 노트북을 ThinQ ON에 더 가까이 배치. 실행 시 출력되는 "판정 참고: 기저 소음/최고" 값에서 최고가 기저 소음+8을 넘는지 확인 |
| 항상 OK (응답 없는데도) | `voice_over_floor_db`를 8→12로 올려보기 |
| 에어컨·선풍기 소음 환경 | 자동 대응됨 — 음성 대역(250~4000Hz)만 측정하고 기저 소음에 자동 적응. `voice_threshold_dbfs`(`--calibrate`)는 '응답 종료 대기'에만 사용 |
| 서버 전송 실패 표시 | Wi-Fi 확인. 전송이 실패해도 `results.jsonl`에 로컬 기록은 남습니다 |
| 판정 로직이 의심될 때 | `python fieldcheck.py --selftest` (오디오 장치 없이 검증) |
| 계속 "건너뜀"만 나옴 | 예약 시간대이거나 예약 조회에 실패한 상태. 메시지에 사유가 표시됩니다. 지금 꼭 점검해야 하면 `--once --force` |
| 아침 요약이 "점검 기록 없음" | 점검 장비가 그날 한 번도 실행되지 않음 → 위 9번 자동 실행이 등록되어 있는지, 노트북이 그 시각에 깨어 있었는지 확인. `logs/schedule.log` 확인 |
| 자동 실행은 되는데 녹음이 안 됨 | 마이크 권한 문제. 맥은 `launchctl kickstart`로 한 번 수동 실행해 권한 창을 띄우고 허용 |
| L2 결과가 안 나옴 | STT 엔진 미설치 — `pip install faster-whisper`. 설치 후에도 안 되면 `config.json`의 `stt.enabled`가 `true`인지 확인 |
| L2가 자꾸 실패로 나옴 | `--transcribe`로 인식 텍스트를 먼저 확인 → 실제 답변에 맞게 `expect_any` 조정. 인식 자체가 부정확하면 `stt.model`을 `small`→`medium`으로 |
| L2 판정이 너무 느림 | `stt.model`을 `base`로 낮추기 (정확도는 다소 하락) |
