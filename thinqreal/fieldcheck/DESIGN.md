# ThinQ Real FieldCheck — Field 자동 점검 시스템 설계

> **상태**: 설계 확정 (2026-07-30) · 구현 전
> **주의**: 이 시스템은 기존 예약 관리 웹사이트(`thinqreal.html` / `thinqreal_admin.html` / `ThinQReal_AppScript.gs`)와 **별도의 시스템**이다. 기존 파일은 이 폴더의 작업으로 수정하지 않는 것을 원칙으로 하며, 연동 지점(Apps Script 엔드포인트 추가, 관리자 탭 추가)만 명시적으로 계획에 따라 반영한다.

---

## 1. 배경

ThinQ Real에서는 ThinQ ON(생성형 AI 엔진 탑재 음성 허브) 기반 AI홈 솔루션의 동작성 점검을 매일 수행한다 — 기동어 발화 후 일상 대화, 가전 제어, 자동화 루틴(모드) 실행. 이 동작이 원활하지 않으면 ThinQ Real 시연 장애뿐 아니라 일반 가정 고객의 컴플레인으로 직결된다.

### 계기가 된 장애 사례 (2026-07-27 주간, ATOM TTS 서버 장애)
- **현상**: 월요일 오후부터 ThinQ ON 음성 발화 후 무응답 빈도 증가 → 화요일 아침 ThinQ Real 시연 불가 수준으로 저하 (일반 고객 집에서도 재현)
- **임시 조치**: Microsoft TTS 서버를 사용하는 최신 SW 버전으로 변경하여 시연 진행
- **해소**: 화요일 12시 CTO부문에서 LG TTS 서버 대안 확보 → 정상 수준 복구
- **지시 사항**: 단건 해결에 그치지 말고, 음성을 포함한 ThinQ ON 서비스 운영을 체계적으로 모니터링하고 이슈/장애에 대응하는 운영 프로세스를 즉시 수립할 것

핵심 교훈: 이번 장애의 증상은 "발화 후 답변 없음"이었다. **주기적으로 말을 걸고 답변 유무를 확인하는 것만으로도** 시연 불가 수준이 되기 반나절 전에 자동 감지가 가능했다.

## 2. 목표

ThinQ Real 공간에 상주하는 점검 장비가 사람 대신 ThinQ ON에게 주기적으로 말을 걸고, 응답을 판정하여 기록하고, 이상 시 담당자에게 즉시 알리는 **감지 → 알림 → 판단 → 기록** 루프를 만든다.

- 장애를 사람이 눈치채기 전에 시스템이 먼저 보고한다 (특히 시연 시작 전)
- 응답 지연시간·성공률 데이터를 축적한다 (공간 운영 목적인 "데이터 축적·고도화"와 부합)
- 기존 예약 관리 시스템의 백엔드(Apps Script + Sheets)·대시보드·메일 인프라를 재활용한다

## 3. 전체 구조

```
[점검 장비: 노트북 + (3단계부터) USB 웹캠]  — ThinQ Real 공간 내 상주, 사외망 AP 접속
        │  ① 저장된 음성 파일(WAV) 재생: 기동어 + 점검 문장
        │  ② 내장 마이크로 ThinQ ON 응답 녹음
        │  ③ (3단계) 웹캠으로 가전 제어 전/후 촬영
        ▼
[판정 로직 (점검 장비에서 실행)]
        │  L1: 응답 유무 + 지연시간   L2: STT → 기대 키워드 매칭   L3: 이미지 비교/기기 상태
        ▼
[백엔드]  POST → Apps Script → Sheets `health_checks` 탭  (엔드포인트 주소는 설정 파일로 분리)
        ▼
[출력]  관리자 대시보드 🩺 자동 점검 탭  +  실패 시 담당자 3명 메일 알림 (기존 MailApp 파이프라인)
```

## 4. 장비 구성

| 장비 | 선택 | 비고 |
|------|------|------|
| 점검 장비 본체 | **남는 노트북 1대** (Windows) | 내장 스피커·마이크 사용. 배터리 = 순간 정전 대비 UPS 효과 |
| 스피커/마이크 | 노트북 내장 | ThinQ ON 근처 1~2m 배치, 기동어 인식되는 볼륨을 찾은 뒤 **고정** |
| 카메라 | 3단계에서 USB 웹캠 추가 | 내장 웹캠은 화면 방향만 촬영 가능 → 스피커 방향(ThinQ ON)과 카메라 방향(가전)을 분리하기 위해 별도 웹캠 필요 |
| 네트워크 | ThinQ Real 전용 AP (사외망) | 현 Apps Script 접근에 제약 없음 |

라즈베리파이는 검토 후 보류 — 상시 가동에는 유리하나 운영자에게 리눅스 학습 비용이 발생하고, 노트북이면 로컬 STT(Whisper)까지 한 대로 해결되므로 노트북을 기본으로 한다. 안정화 후 필요 시 이전 가능(코드 재사용).

### 노트북 상시 가동 설정 (구현 시 적용)
- 덮개를 닫아도 절전 모드 진입 안 함 (전원 옵션)
- 전원 연결 시 화면 꺼짐만 허용, 시스템 절전 금지
- 정전 복구 시 자동 부팅(BIOS) + 로그인 시 점검 프로그램 자동 시작
- Windows 업데이트 자동 재부팅 시간대를 점검 외 시간으로 지정

## 5. 판정 3단계

| 단계 | 확인 내용 | 방식 | 주기(안) | 잡을 수 있는 장애 |
|------|----------|------|---------|------------------|
| **L1** | 발화 후 N초 내 음성 응답이 있는가 + 응답 지연시간 | 음성 활동 감지(VAD) — STT 불필요 | 30분~1시간 간격 | **ATOM TTS 장애가 정확히 이 레벨** (무응답) |
| **L2** | 응답 내용이 기대와 맞는가 | 녹음 → STT → 기대 키워드 매칭 | 1일 2~3회 정밀 점검 | 오응답, 엉뚱한 대화, NLU 이상 |
| **L3** | 가전이 실제로 제어됐는가 | 제어 전/후 이미지 비교 — **AI 불필요**, 아래 상세 | 정밀 점검에 포함 | 제어 경로 장애, 루틴 미실행 |

원칙: **간단한 체크는 자주, 정밀 체크는 정기적으로.** L1의 무응답/지연 데이터만으로도 이번 장애 클래스는 조기 감지된다.

### L3 판정 방식 — AI 엔진 불필요 (2026-08-01 설계 결정, 구축 3단계 착수 전)

**AI 영상 인식은 쓰지 않는다.** L2에서 Whisper가 필요했던 것과 성격이 다르기 때문이다. 음성은 "무슨 말을 했는지" 알아내야 해서 모델이 필요했지만, L3는 **"화면이 변했는지"**만 보면 된다. 다음 세 조건이 문제를 인식(recognition)이 아닌 **비교(comparison)** 문제로 축소한다.

- 카메라가 삼각대에 **고정** — 시점이 변하지 않음
- 쇼룸 배치가 **고정** — 무엇이 어디 있는지 이미 알고 있음
- 질문이 "저게 뭐지?"가 아니라 **"아까와 달라졌나?"**

즉 같은 카메라로 찍은 두 이미지의 픽셀 차이를 계산하는 산술 연산으로 충분하다. **AI가 필요해지는 경계선은 "숫자·문자를 읽어야 할 때"**(예: 에어컨 설정온도 24→26)이며, 그런 대상은 구축 3단계 초기 범위에서 제외한다.

| 대상 | 지표 | 난이도 |
|------|------|--------|
| 조명 켜기/끄기 | 관심영역 **평균 밝기** 변화 | ★ 쉬움 |
| 커튼·블라인드 | 창 영역의 **변화 픽셀 비율** + 경계선 위치 이동 | ★ 쉬움 |
| 무드등 색 변경 | **색상(Hue) 히스토그램** 중심 이동 | ★★ 보통 |
| TV 켜기 | 화면 영역 밝기 + 프레임 간 변동(콘텐츠 재생 여부) | ★★ 보통 |
| 에어컨 설정온도 | 표시부 숫자 판독 | ★★★ **AI/OCR 영역 — 초기 제외** |

**관심영역(ROI) 지정이 핵심 장치**다. 화면 전체를 보면 방문객이 지나가기만 해도 변화로 잡힌다. 대상별로 사각형 좌표를 미리 지정하면 나머지 영역은 아예 보지 않는다. 카메라가 고정이므로 좌표는 한 번만 정하면 된다.

#### 구현 시 주의 — 어려운 쪽은 분석이 아니라 촬영 조건

**① 웹캠 자동 노출 (가장 위험)** — 웹캠은 기본이 자동 노출이라, 조명을 켜면 카메라가 스스로 노출을 낮춰 **결과 이미지의 평균 밝기가 켜기 전과 거의 같아진다.** 정상 동작했는데 "변화 없음 = 실패"로 오판정된다. 마이크 권한 함정(§8)과 같은 부류의 **조용한 실패**다.
- 대응 ①: 노출·게인·화이트밸런스 **수동 고정**. macOS는 USB 웹캠 수동 제어가 제한적이고 Windows는 가능 — **상주 Windows 장비 전환의 추가 근거**
- 대응 ②(고정 불가 시): **상대 비교** — 대상 영역 밝기를 "변하지 않는 벽" 참조 영역 밝기로 나눈다. 카메라가 전체를 어둡게 만들어도 두 영역의 비율은 유지되므로 판정이 살아남는다

**② 촬영 타이밍** — 조명은 즉시지만 커튼은 10~20초 걸린다. "발화 후 N초에 한 장"은 대상마다 튜닝이 필요하고 여전히 빗나간다. **연속 촬영**(발화 직후부터 25초간 1초 간격) 후 시계열에서 변화 구간을 검출하는 방식을 채택한다. 타이밍 튜닝이 불필요하고, 덤으로 **"명령 후 몇 초 만에 움직였는가"**가 남는다 — L1의 `응답 시작`과 같은 성격의 지표.

**③ 카메라 자기진단 (필수)** — 카메라 미연결·렌즈 가림·완전 암전이면 전/후 이미지가 모두 동일해 **가전 장애로 오보**된다. L1의 무음 감지와 같은 구조로, 두 이미지 모두 분산이 임계 이하이면 `점검 장비 문제`로 분류한다.

#### 카메라 vs ThinQ API 상태 조회 — 카메라 채택 (사용자 동의 2026-08-01)
API는 **"서버가 명령을 받았는가"**만 알려준다. 카메라는 **"실제로 물리적으로 움직였는가"**를 본다. 명령은 정상 접수됐으나 커튼 모터가 돌지 않거나 조명이 물리 스위치로 차단된 경우 — 방문객 눈에 보이는 것은 후자이고 API는 이를 잡지 못한다. **쇼룸 시연 품질 보전이 목적이므로 물리 변화 확인이 우선**이며, 둘 다 가능하면 병행한다.

**준비물**: USB 웹캠 1대, 삼각대(고정이 판정 정확도를 좌우), 가전 제어 점검 WAV. **착수 순서**: 조명 1건으로 판정 안정성 확인 → 커튼으로 확대.

#### 구현 확정 사항 (2026-08-05, `rig/vision.py` + fieldcheck.py 통합)
- **사전 검증 실측 통과 (2026-08-04, 맥북 내장 카메라)**: 조명 꺼짐 0.746 ↔ 켜짐 1.063 (상대값 = 대상÷참조), 변화폭 0.317 — 픽셀 비교 판정 성립. 참조 영역(벽)의 절대 밝기도 49나 출렁였으나 상대값이 자동 노출을 상쇄함 — 위 ①의 예측과 대응책이 동시에 실증됨. 내장 카메라는 수동 검증·초기 운용용이며(덮개 각도가 ROI를 좌우) USB 웹캠 전환 시 장치 번호만 교체
- **첫 대상은 웰컴모드 루틴** (조명+커튼+에어컨 동시 구동, 사용자 결정 2026-08-05). 판정은 조명 상대값 1건부터 — 커튼(변화 픽셀 비율)은 다음 단계
- **되물음 대응 — '무조건 확답' 방식**: ThinQ ON이 "…실행할까요?"라고 명령을 확인하는 경우가 있음(단일 기기 명령에서도 발생, 사용자 확인). 대응은 조건 분기가 아니라 **항상 확답 WAV("응. 실행해줘") 재생** — 되물었으면 청취 모드라 접수되고, 이미 실행했으면 기동어 없는 발화라 무시된다(비대칭 역이용). 실시간 STT로 되물음을 감지해 분기하는 안은 STT 소요(수 초) > 되물음 후 청취 창이라 기각. 되물음 후 청취 창이 짧으므로 **L3 시나리오의 녹음 창은 8초로 짧게** 두어 확답이 빨리 나가게 한다. 되물음 발생 여부는 사후 STT로 감지해 note에 기록 — 빈도 증가 자체가 진단 신호(응답 시간 지문과 같은 계열)
- **판정은 '변화'를 본다**: 사전 상태가 이미 목표 상태(예: 조명이 켜진 채 시작)면 명령이 먹혔는지 알 수 없어 '판정 불가(실패)'로 기록. **매일 자동 점검에 편입하려면 점검 후 원상 복구 단계(반대 루틴/명령)가 필요** — 미해결, 사용자와 협의 예정 (에어컨이 켜진 채 남는 문제도 동일)
- **L3의 `latency_ms`는 가전 반응 시간** (확답 재생 종료≈촬영 시작부터 상대값이 기준을 넘기까지) — L1의 '응답 시작'(말)과 성격이 같은 물리 동작판 지표. 가전 단독 제어 vs 루틴(연동) 제어 비교(§5 백로그)의 원자료

### 연산 대기음('띵띵띵…') 구분 — 2026-07-30 현장 테스트 발견
검색이 필요한 질문(예: 영화 추천)에서 ThinQ ON이 답변 전에 연산 대기음을 길게 송출함. 단순 소리 감지로는 이 효과음을 응답으로 오판 → **TTS 장애(듣고 연산음은 내지만 말을 못 함) 상태가 OK로 잘못 판정될 위험** (ATOM TTS 장애가 정확히 이 케이스).

대응: L1 판정을 '지속 소리'가 아닌 **발성 비율 방식**으로 구현 — 1초 구간(speech_window_seconds) 내 임계값 이상 프레임 비율이 70%(speech_voiced_ratio) 이상일 때만 음성 응답으로 인정. 효과음(짧은 띵 + 간격 반복)은 비율이 낮아 걸러지고, 어절 사이 쉼이 있는 말소리는 통과한다. 응답 시작 지연도 큼(현장 관측 ~8초) — 녹음 창은 15~25초 권장.

### L1이 측정하는 것 — '기동어 반응'이 아니라 '질문에 대한 답' (2026-08-02 정리)

혼동하기 쉬운 지점이라 명시한다. 실행 순서(`fieldcheck.py:253~265`)는 다음과 같다.

```
① 기동어 WAV 재생 ("하이엘지")
②  wake_gap 1.5초 대기      ← ThinQ ON의 '띵' 반응은 여기서 발생, 녹음하지 않음
③ 점검 질문 WAV 재생
④  재생 종료 = 녹음 시작 = 0ms   ◀ latency_ms 기준점
⑤  ThinQ ON 발화 시작        → 응답 시작(latency_ms)
```

**'띵'을 의도적으로 배제한다.** ATOM TTS 장애가 "기동어는 듣고 띵도 내지만 말을 못 하는" 상태였으므로, 기동어 반응을 판정 대상으로 삼았다면 그 장애를 정상으로 판정했을 것이다. 배제는 두 겹이다 — ① 녹음이 질문 재생 이후 시작되어 시간상 담기지 않고 ② 담기더라도 발성 비율 판정(위 항목)이 효과음을 걸러낸다.

**현재 구조의 한계와 백로그 (사용자 요청 2026-08-02 — 구축 3단계와 함께 검토)**
기동어 미인식도 결국 질문에 답하지 않으므로 L1 실패로 잡히지만, **"기동어를 못 알아들음"과 "TTS가 말을 못 함"을 구분하지 못한다.** 둘 다 즉시 대응이 필요한 상태이고 현장에서 한 번 말을 걸면 즉시 구분되므로 초기 구현에서는 제외했다.
- **넣어야 할 시점**: L1 실패가 반복 기록되는데 현장에서는 정상으로 보이는 경우. 기동어 인식률 저하는 조용히 진행되는 열화라 데이터 없이는 발견이 늦다
- **구현 방법**: 기동어 재생 직후 `wake_gap` 구간(1.5초)을 별도 녹음 → '띵' 존재 여부만 판정(발성 비율이 아닌 단순 피크 검출 — 효과음을 *찾는* 것이므로 기준이 반대) → 결과를 `note` 또는 신설 필드에 기록. 판정 단계를 늘리지 않고 L1의 부가 정보로 붙인다
- **주의**: 기기 모델·펌웨어에 따라 기동어 반응음이 없거나 바뀔 수 있으므로, 이 판정을 실패 조건으로 삼지 말고 **진단 참고값**으로만 쓴다

### 응답 시간은 처리 경로의 지문 (2026-08-02 관찰 — 강원석)

08-01 실측에서 시나리오별 '응답 시작'이 크게 갈렸다: 시간 질문 **150ms** / 일상 대화 **2,910ms** / 날씨 **4,620ms**. 처음에는 150ms를 "발화 종료 전에 응답을 시작했을 가능성"으로 의심했으나, 처리 경로 관점의 해석이 더 설득력 있다:

| 질문 | 추정 처리 경로 | 응답 시작 |
|------|--------------|----------|
| 지금 몇 시야? | **기기 내 즉답** — AI 엔진 호출 없음 | 150ms |
| 오늘 기분 어때? | 생성 엔진 경유 (저계산·정형 답변) | 2,910ms |
| 오늘 날씨 어때? | 생성 엔진 + **외부 서비스(AccuWeather) 연동** | 4,620ms |

즉 응답 시간은 단순 성능 지표가 아니라 **그 질문이 어떤 경로를 타는지 보여주는 지문**이다. 이 관점의 실익:

- **경로별 기준선(baseline)이 다르다** — "시간 질문이 3초 걸림"은 정상 범위여도 이상 신호다. 전체 평균이 아니라 시나리오별 추이로 봐야 한다
- **지연 증가의 위치를 특정할 수 있다** — 날씨만 느려지면 외부 연동 경로, 전부 느려지면 엔진/인프라
- **L3 확장 시 비교 설계 (백로그)**: ① 가전 **단독 제어**("조명 켜줘")와 ② **서비스 연동 제어**의 응답 시간을 나눠 측정하면 제어 경로의 구간별 소요가 드러난다. 시나리오 설계 시 두 유형을 의도적으로 포함할 것
- 데이터가 며칠 쌓이면 시나리오별 정상 범위를 산출해, 실패 전 단계인 **"느려지는 중"을 조기 신호**로 쓸 수 있다 (Phase 2 검토)

### 정상(定常) 소음 환경 대응 — 2026-07-30 현장 테스트 발견 2
에어컨·선풍기 가동 중에는 절대 음량 임계값이 소음 위로 캘리브레이션되어, ThinQ ON이 정상 응답해도 FAIL로 오판됨. 대응: **적응형 대역 판정** — ① 음성 대역(250~4000Hz) 에너지만 측정해 저주파 팬 소음을 배제하고, ② 녹음마다 하위 10퍼센타일을 '기저 소음'으로 자동 추정, ③ 기저 소음+8dB(voice_over_floor_db) 이상만 발성으로 인정. 절대 임계값(voice_threshold_dbfs)은 '응답 종료 대기'에만 사용. 기동어 후 대기는 1.5초로 상향.

### 생성형 답변의 길이 변동성 대응
ThinQ ON은 생성형 AI라 답변 길이가 크게 변동한다 (예: 영화 추천 질문에 수십 초 답변). 이에 대한 원칙:
- **L1 판정은 답변의 '시작'만 본다** — 응답 시작 여부·지연시간이 측정 대상이므로 답변이 길어도 판정은 정확하다. 녹음 창(listen_seconds)은 앞부분만 담으면 충분.
- **시나리오 사이에는 '조용해질 때까지 대기' — 판정 결과와 무관하게 항상** — 앞 답변이 끝나기 전에 다음 기동어를 재생하면 씹히거나 판정이 오염됨. 무응답 판정이어도 실제 답변이 녹음 창 이후 늦게 시작될 수 있으므로(현장 관측: 영화 질문의 답변이 다음 시나리오 기동어를 씹음) 항상 대기한다. post_silence_seconds(2초) 연속 무음 확인, max_response_wait_seconds(60초) 상한.
- **점검 문장은 짧은 답이 나오는 질문으로 선정** — 영화 추천처럼 긴 검색·긴 답변을 유발하는 질문은 점검 소요 시간을 크게 늘림. 순수 일상 대화는 "오늘 기분 어때?" 수준의 즉답형 질문 권장.
- **L2(내용 판정)도 앞부분 N초의 STT로 충분** — 기대 키워드는 대개 답변 서두에 나온다. 필요 시 점검 문장을 짧은 답이 나오는 형태로 조정.

### 입력 음성의 재현성 (중요)
점검 문장은 매번 TTS로 새로 생성하지 않고, **한 번 생성/녹음한 WAV 파일로 고정**한다. 같은 음성·같은 볼륨·같은 위치에서 재생되어야 "오늘 실패가 ThinQ ON 문제인지, 입력이 달라진 탓인지"를 구분할 수 있다. 스피커 볼륨과 배치는 캘리브레이션 후 변경 금지.

## 6. STT 방침 — 로컬 Whisper 확정 (2026-07-31 구현)

당초 안은 "개인 테스트는 Google Cloud STT(방법 A) → 공식 운영 시 로컬 Whisper(방법 B) 전환"이었으나, **처음부터 로컬 Whisper로 구현**했다. 이유:

- **보안 검토를 나중으로 미루지 않아도 됨** — 공간의 음성이 외부로 나가지 않으므로, 팀 공식 운영으로 격상할 때 STT 경로에 대한 추가 검토가 불필요하다. 나중에 전환하면 그 시점에 재검증·재작업 비용이 발생한다.
- **사외망 단절 시에도 판정 가능** — 클라우드 STT는 네트워크가 끊기면 L2 자체가 멈춘다. 정작 장애 상황에서 판정이 안 되는 구조는 점검 시스템으로 부적합하다.
- **과금·할당량 관리 불필요** — 개인 클라우드 계정 결제 수단을 운영 시스템에 묶지 않아도 된다.

구현: `rig/stt.py` — `faster-whisper`(CPU에서 수 배 빠름) 우선, 없으면 `openai-whisper` 폴백, **둘 다 없으면 L2를 조용히 건너뛰고 L1은 그대로 동작**(하위 호환). 엔진·모델 크기는 `config.json`의 `stt`로 교체 가능하므로, 향후 다른 엔진(사내 STT 등)으로 바꿀 때도 이 파일 하나만 손대면 된다.

### 내용 판정 규칙
- `expect_any` (하나라도 일치) / `expect_all` (전부 일치) / 둘 다 없으면 최소 길이만 확인 (자유 대화용)
- **`forbid_any` (회피 표현 감지)** — `모르겠 / 죄송 / 다시 말씀 / 이해하지 못 / 지원하지 않 / 확인할 수 없 / 알 수 없`. **L2의 핵심 가치**: ThinQ ON이 "죄송해요, 잘 모르겠어요"라고 답하면 L1은 통과(소리는 났으므로)하지만 실제로는 실패다. 이 유형은 L1으로는 원리상 잡을 수 없다.
- **L2는 L1 통과 건에 대해서만 판정** — 응답이 없으면 판정할 말이 없고, 같은 실패를 두 건으로 세면 통계가 왜곡된다. 따라서 L2 성공률은 "응답한 것 중 내용까지 맞은 비율"로 해석한다.
- 키워드 튜닝은 `--transcribe`로 **이미 저장된 녹음**에 대해 발화 없이 반복 시험한다.

### STT 오인식을 어디까지 감수할 것인가 (2026-08-01 현장 확인)
실제 인식 결과에 오류가 섞인다: `사용자님`→`새형제님`, `등촌동`→`등천동`. **이를 교정하려 하지 않는다.** 판정 대상은 "질문에 맞는 답을 했는가"이지 "받아쓰기가 정확한가"가 아니며, 위 사례 모두 기대 키워드(`날씨`·`기온`)가 살아남아 정상 통과했다.
- **설계 원칙**: `expect_any`에 **동의어를 여럿** 둔다. 키워드 하나에 의존하면 오인식 한 번이 곧 오판정이 된다. 다중 키워드가 STT 오차에 대한 완충 장치다.
- 정확도 개선은 비용이 낮은 순서로: ① `vocabulary_hint`(initial_prompt)에 고유명사 추가 — 비용 0 ② 모델 `small`→`medium` ③ LLM 문맥 교정 — **채택하지 않음**(외부 AI 의존이 생기고 §6의 로컬 처리 원칙을 깨뜨리는 반면, 판정 정확도 기여는 미미)

## 7. 점검 시나리오

시나리오 항목: `id`, `구분(일상대화/가전제어/루틴)`, `발화 문장(WAV 파일명)`, `기대 키워드`, `판정 단계(L1/L2/L3)`, `L3 촬영 대상`, `사용 여부`.

**Sheets 편집은 보류 (2026-07-31 판단)** — 당초 "운영자가 코드 수정 없이 시나리오를 추가"하는 안이었으나, 새 시나리오는 **점검 장비(노트북)에 WAV 파일이 먼저 존재해야** 동작한다(재현성 원칙 §5). 시트에 문장만 추가해도 점검 장비가 발화할 수 없으므로, 시트 관리만으로는 목적을 달성하지 못한다. 현재는 `config.json`으로 관리하고, 필요해지면 **기대/회피 키워드만** 시트로 빼는 방식을 검토한다 (키워드는 ThinQ ON 답변이 바뀔 때마다 조정이 잦은 반면 WAV 의존성이 없어 시트 관리에 적합).

초기 시나리오(안):
1. **일상 대화 (순수)** — 외부 서비스와 무관한 자유 질문 (L1·L2)
2. **일상 대화 (서비스 연계)** — 날씨 질문으로 AccuWeather 연동 경로 점검 (L1·L2)
3. **가전 제어** — 조명 켜/끄기 (L1·L2·L3: 이미지 밝기 차이로 판정 용이)
4. **자동화 루틴/모드 실행** 1건 (L1·L2·L3)

일상 대화를 두 타입으로 분리하는 이유: 순수 대화만 실패하면 **생성형 엔진 자체** 장애, 날씨만 실패하면 **외부 서비스(AccuWeather) 연동 경로** 장애로 원인을 구분 진단할 수 있다.

## 8. 예약 시스템 연동

**구현 완료 (2026-07-31, `rig/booking.py`)**
- 점검 전 기존 `GET ?type=availability&date=` 조회 → **회피 대상 슬롯 시간대는 점검 자동 스킵** (시연 중 기동어 발화 방지)
- 회피 대상: 확정 예약(`bookedSlots`) + 관리자 차단 슬롯(`blockedSlots` — 촬영 등 운영 사정). 대기중(`pendingCounts`)은 기본 제외
- 여유 시간: 슬롯 시작 **20분 전** ~ 종료 **10분 후** (방문객 조기 도착·지연 퇴장 대비). `guard_before_minutes`/`guard_after_minutes`로 조정

- 슬롯 시간표(`slot_windows`)는 config에 분리 — 예약 시간표가 바뀌어도 코드 수정 불필요
- 수동 강행: `--once --force` (시연 중이 아님을 직접 확인 후 사용)

- **필요했던 이유**: 2026-08-01 아침 요약이 "⚠ 점검 기록 없음"으로 발송됨. 점검 장비가 수동 실행에만 의존해 그날 한 번도 돌지 않은 것. 판정 로직이 아무리 정확해도 **실행되지 않으면 무의미**하므로 자동 실행은 선택이 아닌 필수 구성요소
- 스피커·마이크를 쓰므로 **사용자 로그온 세션**에서 실행되어야 함

**macOS 마이크 권한 제약 (2026-08-01 현장 확인 — 중요)**
launchd가 `python3`을 직접 실행하면 macOS가 마이크 권한 요청 창을 **띄우지 않고 무음을 반환**한다. 앱 번들이 아닌 실행 파일은 TCC(개인정보 보호) 대상으로 인정되지 않기 때문이며, 시스템 설정의 마이크 목록에도 나타나지 않아 수동 허용도 불가능하다. **오류가 나지 않고 조용히 실패**하는 것이 특히 위험하다 — 실제로 이 상태에서 3건 모두 FAIL로 기록되어 ThinQ ON 장애로 오인할 뻔했다.
- 대응 ①: launchd → `open -a Terminal <run_once.command>` 경유 실행. 터미널은 정식 앱 번들이라 권한 창이 정상 표시되고, 한 번 허용하면 유지된다
- 대응 ②: 무음(모든 프레임 -120dB) 자동 감지 → 콘솔 경고 + 시트 `note`에 "점검 장비 설정/권한 문제(ThinQ ON 장애 아님)" 기록 + `--mic-test` 진단 명령
- Windows에는 이 제약이 없음(작업 스케줄러가 로그온 세션에서 실행하면 마이크 접근 가능) — 상주 장비 전환 시 자연 해소

**미구현 (Phase 2 스케줄링 고도화)**
- **각 예약 슬롯 시작 30분 전 L1 스모크 테스트** → 실패 시 즉시 메일 ("N회차 예약 전 점검 실패 — 시연 전 확인 필요")
  - ※ 현재 회피 여유(시작 20분 전)와 겹치므로, 도입 시 "슬롯 전 스모크 테스트는 회피 예외" 처리 필요
- 그 외 시간대 30분~1시간 간격 L1 점검 (현재는 `loop_interval_minutes` 단일 주기)

## 10. 사내 이관 대비 설계 원칙 (필수 준수)

기존 예약 관리 시스템이 사내 이관 준비 중이므로, FieldCheck도 함께 이관될 것을 전제로 설계한다.

1. **엔드포인트 주소는 설정 파일로 분리** — 점검 장비 코드는 "설정에 적힌 주소 하나로 결과를 보내는 프로그램". 이관 시 주소 한 줄 교체로 끝나야 한다.
2. **인증은 API 키 방식** — 처음부터 요청에 키를 실어 보내는 구조로 만들어, 이관 시 키만 교체.
3. **미디어(녹음/사진) 저장 위치도 설정으로 분리** — Sheets에는 메타데이터만, 파일은 별도 저장(테스트: 점검 장비 로컬 + 실패 건만 업로드 검토).
4. **데이터 스키마는 단순 행(JSON) 구조 유지** — 어떤 DB로도 매핑 가능하게.
5. **네트워크**: 현재 점검 장비는 사외망 AP라 문제 없음. 이관 후 사내 시스템 접근 가능 여부는 이관 시점에 담당 부서와 확인 (미해결 항목).
